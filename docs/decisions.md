# Решения по MVP (2026-11-20)

Принято без владельца; всё можно пересмотреть.

## Хранилище: SQLite (WAL), не PostgreSQL
- Один писатель (воркер) и читатели (сайт). Объём MVP — десятки МБ. SQLite в WAL-режиме справляется без отдельного сервера.
- PostgreSQL на сервере не установлен, а MySQL занят другими проектами.
- Схема переносится в Postgres почти один к одному (`app/websec/db.py`), если понадобятся очередь с `SKIP LOCKED` или несколько воркеров.

## Стек
- Python 3.14 в venv `~/venvs/websec`.
- Сайт: FastAPI + Jinja2 с серверным рендерингом, юнит `websec`, uvicorn на 127.0.0.1:8795 за nginx.
- Воркер: один процесс `websec-worker` со своим планировщиком. Интервал каждого источника хранится в таблице `sources.interval_sec` и меняется без деплоя. Отдельные systemd-таймеры не нужны: по ним сложнее вести состояние и алерты.

## Модель данных
- `raw_items` — сырые записи источников. Хранятся только совпавшие с каталогом или уже известные уязвимости.
- `facts` — нормализованные факты одного источника об уязвимости. Строка `vulns` каждый раз пересчитывается из всех фактов, поэтому результат детерминирован и не зависит от порядка прихода данных.
- Канонический ID — CVE. Если CVE нет, используется GHSA или OSV. Когда у GHSA появляется CVE, запись переименовывается и все связи переносятся.
- Если advisory упоминает два разных CVE, они остаются двумя уязвимостями: CVE друг в друга не сливаются.
- `events` — события: published, scored, kev, fix, epss_high. Публикация в TG срабатывает от событий, поэтому дублей постов нет.

## Источники (этап 1 + часть этапа 3)
- **CVE: cvelistV5 delta-релизы** — накопительный zip «изменения с полуночи UTC», выходит каждый час, проверяем раз в 10 минут; для прошлых дней — `end_of_day`. Без git clone, ~5–12 МБ в сутки. Бэкфилл — 30 дней.
- **OSV.** Бэкфилл — полная история пакетов каталога через `/v1/query`. Дельты — `modified_id.csv` с ETag. MAL-* (вредоносные пакеты) пропускаем. GitHub Advisory приходит отсюда (GHSA в OSV), отдельный коллектор GraphQL не нужен.
- **CISA KEV** — JSON с ETag.
- **EPSS** — API FIRST, только наши CVE, раз в сутки после выхода новой даты.
- **cveapi** — CVE-запись из CVE Services для уязвимостей, пришедших из OSV или KEV без записи cvelist: старые CVE из KEV и история пакетов.
- **nginx.org** — первый вендорский парсер: точные границы версий и оценка nginx.
- **NVD не используем:** с апреля 2026 он неполный, а CPE даёт и ADP CISA в самой CVE-записи.

## Каталог и шум
- 50 продуктов в `app/websec/catalog.py`. Продукт распознаётся по vendor|product (регэкспы, сверены с реальными данными cvelist и KEV), CPE, packageName (дистрибутивы, Red Hat), координатам OSV и KEV vendorProject|product.
- **Ядро Linux** (`high_only`) — 500+ CVE в день без оценки. Берём только KEV, CVSS ≥ 9, сетевой вектор с CVSS ≥ 8 или EPSS ≥ 10%. Остальные CVE ядра даже не сохраняем.
- **Плагины WordPress не берём:** в каталоге только ядро WP (как в ТЗ).
- **Лента — окно 45 дней** по `feed_ts = max(published, kev_added)`, поэтому старая уязвимость, попавшая в KEV, поднимается наверх. На странице продукта — вся известная история.

## Оценки
- CVSS не придумываем. Порядок выбора: CNA 3.1 → CNA 3.0 → CNA 4.0 → CISA-ADP → GHSA (OSV). Источник оценки всегда показан. Для OSV оценка CVSS 3.x считается из вектора кодом.
- **Priority (правило, без ИИ):**
  - KEV → CRITICAL, а при CVSS Medium/Low → HIGH;
  - иначе — полоса CVSS;
  - EPSS ≥ 50% поднимает приоритет на одну ступень;
  - без оценки — UNRATED.
- **Своя оценка ИИ** (`our_score`, «насколько касается типичного веб-сервера») показывается отдельно и подписана как AI.

## ИИ (решение владельца 2026-11-20: без API)
- LLM API и ключи не используем. Разбор делает локальный клиент `claude -p` по подписке по схеме «разбудить — получить — заснуть».
- **Запуск:** таймер `websec-ai.timer` раз в 10 минут запускает `python -m websec.ai`. Если в ленте есть записи за 7 дней без разбора (или их факты изменились), он будит `claude -p` на пачку до 8 записей, сохраняет JSON и завершается. Пачка из 8 разбирается примерно за минуту.
- **Лимиты, чтобы беречь подписку:** не больше 2 пачек за запуск и 6 в час. Сначала разбираются CRITICAL, HIGH и KEV.
- **Защита от выдумок:**
  - вход — только собранные факты, ответ — строгая JSON-схема;
  - исправленные версии сверяются кодом с источниками, неподтверждённые отбрасываются и помечаются;
  - ссылки берутся только из входных данных.
- **Кэш** по хэшу входных фактов: повторный разбор только при изменении данных.
- **Telegram:** срочный пост ждёт ИИ-разбор до 20 минут, потом уходит без него.

## Telegram
- Очередь `tg_queue` с лимитом 15 сообщений в минуту и обработкой 429.
- **Сразу постом:** новые CRITICAL/HIGH или KEV, «теперь эксплуатируется» (KEV) и повышение оценки до HIGH/CRITICAL.
- **Остальное** — дайджестом раз в сутки в 09:00 UTC.
- Срочный пост ждёт ИИ-резюме до 20 минут.
- События старше 36 часов — бэкфилл, в TG не уходят.
- Канал задаётся в `WEBSEC_TG_CHAT` юнита `websec-worker`. Пока канала нет — тестовый режим: топик Sec, не больше 3 постов в сутки.

## Сайт
- Пока только EN, без языкового префикса.
- Для языков план — пути `/ru/`, `/es/`… (а не поддомены): общий авторитет домена, один сертификат, hreflang и canonical. Переводы — из канонического EN с глоссарием, с кэшем.
- `noindex` до выхода на боевой домен.
- RSS: `/feed.xml?product=&prio=&kev=`. API: `/api/v1/vulns`, `/api/v1/vulns/{id|alias}`, `/api/v1/products`, OpenAPI — `/api/docs`.
- `/status` — состояние коллекторов. Алерты в топик Sec: источник падает 3 раза подряд или cvelist молчит больше 6 часов.

## Домен websec.in (2026-11-20)

- Сайт переехал с libsec.alid.in на https://websec.in (куплен на Dynadot). Старый адрес, `www` и любые `*.websec.in` — 301 на `https://websec.in` с сохранением пути.
- DNS — Dynadot DNS (`ns1/ns2.dyna-ns.net`): `@` и `*` → A 51.161.35.179. Правка: `sudo python3 /usr/local/lib/dynadot-dns.py get|set-web` (ключ — `DYNADOT_ENV` в `dok`, файл `/root/.secrets/dynadot.env`). `set_dns2` у Dynadot перезаписывает всю зону — скрипт всегда отправляет полный список.
- Сертификат `websec.in` + `*.websec.in` (ECDSA, Let's Encrypt), dns-01, хуки `/usr/local/sbin/dynadot-acme-auth|cleanup`, продление — обычный `certbot renew`. Dynadot публикует изменения медленно (минуты), хук ждёт TXT на обоих NS до 20 минут.
- `noindex` пока остаётся (снят в тот же день, см. ниже).

## Бой, языки на поддоменах (2026-11-20, решение владельца)

- websec.in — боевой домен: `noindex` снят, robots.txt открыт (кроме `/api/`), у каждого поддомена свой `/sitemap.xml` с xhtml:link на все языковые версии. Бренд на сайте — WebSec (кодовое имя проекта остаётся websec).
- Языки: английский на websec.in, переводы на двухбуквенных поддоменах `es pt fr de ru zh ja`. Отменяет прежний план с путями `/ru/`. Арабский и хинди не взяты: RTL-вёрстка, и аудитория обычно читает техническое на английском. Добавить язык: код в `i18n.LANGS`, `ai.TR_NAMES`, `tools/i18n_gen.py NAMES`, поддомен в nginx, затем `python3 tools/i18n_gen.py <код>`.
- Интерфейс: словари `app/i18n/<lang>.json` (ключ — английская строка из `_('…')` в шаблонах). Новые строки: `python3 tools/i18n_gen.py es pt fr de ru zh ja` переводит недостающие через `claude -p`, тест `test_i18n` ловит пропуски и сломанные плейсхолдеры/теги.
- Тексты ИИ-разборов переводит тот же `websec-ai.timer` после разбора: `claude -p --model sonnet`, один вызов = 1 язык × до 10 записей, не больше 8 вызовов в час. Перевод, где потеряно хоть одно число или версия оригинала, отбрасывается. Описания CVE не переводятся (помечены как английский оригинал).
- SEO: страница уязвимости на языке индексируется только при актуальном переводе разбора, иначе `noindex,follow`. hreflang и sitemap включают только индексируемые версии, плюс x-default на английскую. Страницы с фильтрами и поиском — `noindex,follow`. На каждой странице canonical, Open Graph и JSON-LD (WebSite с SearchAction; TechArticle и BreadcrumbList на уязвимостях; BreadcrumbList на продуктах).
- Перелинковка: хлебные крошки; на уязвимости — «ещё уязвимости продукта» (по 6 на 2 продукта) и ссылки на продукты из таблицы версий; на продукте — соседние продукты категории; на ленте — все продукты по категориям; переключатель и список языков ведут на ту же страницу; ссылка на GitHub в шапке, подвале и в разделе About.

## llms.txt и schema.org (2026-11-20)

- `/llms.txt` (формат llmstxt.org) на каждом поддомене: что за сайт, метод, доступ к данным (API, OpenAPI, RSS), страницы, все продукты, свежие критичные/KEV, исходники. Ссылки ведут на поддомен запроса. Текст на английском, разборы в списке — на языке поддомена.
- `/llms-full.txt` — 500 свежих записей ленты в Markdown: приоритет, CVSS/EPSS/KEV, резюме, действие, проверенные исправленные версии.
- JSON-LD: Organization (`/#org`, sameAs GitHub) и WebSite с SearchAction — везде. Лента — CollectionPage + ItemList и Dataset (`/#dataset`, раздачи RSS/JSON). Продукты — CollectionPage + ItemList. Продукт — CollectionPage (about SoftwareApplication) + BreadcrumbList. About — AboutPage, Dataset, SoftwareSourceCode. Уязвимость — TechArticle (author/publisher, isBasedOn: запись CVE и ссылки, keywords, isPartOf dataset, translationOfWork у переводов) + BreadcrumbList.

## API для агентов (2026-11-20, решение владельца)

- API только на websec.in и только на английском: `/api*` с языковых поддоменов — 301 на главный домен.
- Любой ответ начинается с `result` (true/false), `doc` (ссылка на `/api/doc`), `about`, `generated`; ошибки — `result: false` + `error`, статус 400/404.
- `/api/high10` — последние N (по умолчанию 10, до 50) записей CRITICAL+HIGH по `feed_at`, полные (описание, affected, ссылки, ИИ-разбор), с `fixed_versions` и `action` наверху. Фильтры `product=a,b`, `priority`, `kev`, `n`. Для агента владельца, который по расписанию чинит серверы.
- `product=` во всех списках принимает несколько слагов через запятую. `/api/v1/products` теперь тоже в конверте (`items`).
- Справка — `docs/api.md`, отдаётся как `/api/doc` (text/plain). CORS открыт, `Cache-Control: max-age=60`.

## «Как это работает», превью для соцсетей (2026-11-20, решение владельца)

- `/how` на всех языках: пайплайн, что делает ИИ, где брать данные, чем полезно — простыми словами, плюс примеры запросов к API (curl на websec.in, образец ответа). Ссылка в шапке, в sitemap и llms.txt.
- На каждой странице Open Graph и Twitter card `summary_large_image`: og:image 1200×630 + размеры, alt, twitter:title/description/image.
- Картинки рисует `websec/og.py` (Pillow, шрифт Noto Sans CJK из пакета `fonts-noto-cjk`) по запросу, кэш в памяти, `Cache-Control: max-age=86400`. Свои у уязвимости (`/og/vuln/{id}.png`: ID, продукты, заголовок на языке поддомена, «исправлено в», плашки приоритета, KEV, CVSS, EPSS; полоса цвета приоритета) и продукта (`/og/product/{slug}.png`), у остальных страниц — `/og/page/{name}.png` и общая `/og/site.png`. У уязвимостей в URL картинки `?v=` от даты изменения и наличия разбора, чтобы соцсети подтягивали новую версию.
- Строки из `_('…')` в `web.py` тоже собирает `tools/i18n_keys.py`.
- Тест `test_web` гоняет страницы, картинки и API на живой БД (если она есть). Повод: `_()` с подстановкой `{s}` падал (имя совпадало с аргументом) и все страницы уязвимостей с событием CVSS отдавали 500.
